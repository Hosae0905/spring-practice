## 로그인 처리1 - 쿠키, 세션

### 로그인 처리하기 - 쿠키 사용
- 쿼리 파라미터를 계속 유지하면서 보내는 것은 매우 어렵고 번거로운 작업이기 때문에 쿠키를 사용한다. 
- 쿠키에는 영속 쿠키와 세션 쿠키가 있다.
  - 영속 쿠키: 만료 날짜를 입력하면 해당 날짜까지 유지
  - 세션 쿠키: 만료 날짜를 생략하면 브라우저 종료시 까지만 유지
- 쿠키는 보안상 문제가 많다.

### 쿠키와 보안 문제
- 쿠키 값은 임의로 변경할 수 있다.
- 쿠키에 보관된 정보는 훔쳐갈 수 있다.
- 해커가 쿠키를 한 번 훔쳐가면 평생 사용할 수 있다.
- 이러한 보안 문제를 해결하기 위한 대안이 필요하다.
- 쿠키에 중요한 값을 노출하지 않고 사용자 별로 예측 불가능한 임의의 토큰을 노출하고 서버에서 토큰과 사용자 ID를 매핑해서 인식한다. 그리고 서버에서 토큰을 관리한다.
- 토큰은 해켜가 임의의 값을 넣어도 찾을 수 없도록 예상 불가능해야 한다.
- 해커가 토큰을 탈취해도 시간이 지나면 사용할 수 없도록 서버에서 해당 토큰의 만료시간을 짧게 유지한다.
- 해킹이 의심되는 경우 서버에서 해당 토큰을 강제로 제거하면 된다.

### 로그인 처리하기 - 세션 동작 방식
- 쿠키에 중요한 정보를 보관하지 못하니깐 중요한 정보를 모두 서버에 저장하고 클라이언스와 서버는 추정 불가능한 임의의 식별자 값으로 연결해야 한다.
- 서버에 중요한 정보를 보관하고 연결을 유지하는 방법을 세션이라고 한다.
- 클라이언트와 서버는 결국 쿠키로 연결이 되어야 한다.
- 중요한 포인트는 회원과 관련된 정보는 클라이언트에 전달하지 않는다.
- 세션 아이디만 클라이언트에 보낸다.

### 로그인 처리하기 - 세션 직접 만들기
- 세션은 생성, 조회, 만료 세 가지 기능이 필요하다.
- 세션은 특별한 것은 아니고 단지 쿠키를 쓰는데 서버에서 데이터를 유지하는 방법이다.

### 로그인 처리하기 - 서블릿 HTTP 세션 1
- 서블릿은 세션을 위해 HttpSession 이라는 기능을 제공하는데 직접 구현한 세션보다 더 잘 구현되어 있다.
- 서블릿을 통해 HttpSession을 생성하면 JSESSIONID 라는 쿠키를 생성한다.
- HttpServletRequest를 통해서 세션 정보를 가져올 수 있다.
- getSession() 메서드를 통해 세션을 생성할 수 있는데 2가지 옵션이 존재한다.
  - getSession(true)
  - 세션이 있으면 기존 세션을 반환하고, 없으면 새로운 세션을 생성해서 반환한다.
  - getSession(false)
  - 세션이 있으면 기존 세션을 반환하고, 없으면 새로운 세션을 생성하지 않고 null을 반환한다.
  - 기본 값은 getSession(true)

### 로그인 처리하기 - 서블릿 HTTP 세션 2
- 스프링에서 제공하는 @SessionAttribute 애노테이션을 사용하면 깔끔하게 코드를 작성할 수 있다.
- 로그인을 처음 시도하면 URL에 jsessionid 를 포함하고 있는 것을 확인할 수 있다.
- 이렇게 되는 이유는 만약에 웹 브라우저가 쿠키를 지원하지 않을 때 쿠키 대신 URL을 통해서 세션을 유지하는 방법이다.
- 해당 방법을 사용하려면 URL에 해당 세션 값을 계속 포함해서 전달해야 한다.
- 처음에 저렇게 되는 이유는 서버 입장에서는 웹 브라우저가 쿠키를 지원하는지 아닌지 최초에는 판단하지 못하기 때문이다.
- 이런 방법을 사용하지 않으려면 아래의 옵션을 넣어주면 된다.
  - server.servlet.session.tracking-modes=cookie

### 세션 정보와 타임아웃 설정
- 세션에서 여러 정보들을 출력해볼 수 있다. (세션 아이디, 유효 시간, 생성 시간 등)
  - sessionId = 세션 ID
  - maxInactiveInterval: 세션의 유효 시간
  - creationTime: 세션 생성일시
  - lastAccessedTime: 세션과 연결된 사용자가 최근에 서버에 접근한 시간, 클라이언트에서 서버로 sessionId를 요청한 경우에 갱신
  - isNew: 새로 생성된 세션인지, 아니면 이미 과거에 만들어졌고, 클라이언트에서 서버로 sessionId를 요청해서 조회된 세션인지 여부
- 세션 타임아웃 설정이 중요하다.
- 사용자가 로그아웃을 호출하면 invalidate()를 호출되기 때문에 세션이 정상적으로 삭제된다.
- 하지만 대부분의 사용자는 로그아웃을 호출하지 않고 그냥 브라우저를 닫아버린다.
- 이럴 경우 HTTP의 비연결성 특징으로 인해 서버 입장에서는 해당 사용자가 웹 브라우저를 종료한 것인지 인식할 수 없다.
- 따라서 서버에서 세션 데이터를 언제 삭제해야 하는지 판단하기 어렵게 되고 세션 정보를 무한정 보관하게 되버린다.
- 무한정 보관하게 되면 세션과 관련된 쿠키가 탈취될 경우 오랜 시간이 지나도 악의적인 요청을 할 수 있다.
- 세션은 기본적으로 메모리에 생성되기 때문에 메모리의 크기가 무한하지 않고 꼭 필요한 경우에만 사용해야 한다.
- 세션의 종료 시점을 정할때 단순히 30분 이렇게 잡는 것이 아닌 사용자의 가장 최근에 요청한 시간을 활용해야 한다.
- 예를 들면 사용자가 가장 최근에 요청한 시간을 기준으로 30분 정도 세션을 유지시켜 주고 삭제할 수 있도록 해주는 것이다.
- HttpSession은 이 방식을 사용한다.
- 스프링 설정에 옵션을 넣어서 글로벌로 적용시킬 수 있다.
  - server.servlet.session.timeout
  - 글로벌 설정 시 분 단위로 설정해야 한다.
- 특정 세션 단위로 시간 설정도 가능하다.
  - setMaxInactiveInterval()
- 실무에서 조심해야할 점으로는 최소한의 데이터만 보관해야 한다. 왜냐하면 보관한 데이터 용량 * 사용자 수로 세션의 메모리 사용량이 급격하게 늘어나서 장애로 이어질 수 있다.
- 그 외에도 세션의 시간을 너무 길게 가져가면 메모리 사용이 계속 누적될 수 있으므로 적당한 시간을 선택하는 것이 필요하다.
- 기본이 30분이라는 것을 기준으로 고민하면 된다.
